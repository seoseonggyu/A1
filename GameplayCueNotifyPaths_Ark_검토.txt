GameplayCueNotifyPaths에 /Ark 플러그인 경로를 추가한 것에 대한 리스크 검토
(작성일: 2026-08-26)

------------------------------------------------------------
1. 무엇을 했나
------------------------------------------------------------
피격 데미지 숫자 팝업(GCN_DamageTaken 등 GameplayCueNotify BP)을 Ark GameFeature
플러그인 콘텐츠 폴더(/Ark/...)에 저장하고 싶어서, Config/DefaultGame.ini의
[/Script/GameplayAbilities.AbilitySystemGlobals] 섹션에 아래 두 줄을 추가함:

    +GameplayCueNotifyPaths=/Ark/GameplayCueNotifies
    +GameplayCueNotifyPaths=/Ark/GameplayCues

기존에는 /Game/GameplayCueNotifies, /Game/GameplayCues 두 경로만 등록되어 있었고,
그래서 /Ark 하위에 GameplayCueNotify BP를 저장하면 에디터가
"Invalid GameplayCue Path" 경고를 띄웠음. 위 설정 추가 후 경고 사라지고 PIE에서
정상 동작 확인됨.

------------------------------------------------------------
2. 왜 지금은 리스크가 낮다고 판단했나
------------------------------------------------------------
- Config/DefaultGame.ini의 AssetManagerSettings에 Ark가
  SpecificAssets=("/Ark/Ark.Ark"), CookRule=AlwaysCook 로 등록되어 있음.
- CLAUDE.md 기준 Ark는 "ExplicitlyLoaded, 기본 Registered" — 즉 게임이 시작되면
  항상 마운트되는 콘텐츠 전용 GameFeature.
- GameplayCueNotifyPaths는 config 로드 시점에 정적으로 읽히는 배열이고,
  GameplayCueManager가 실제로 이 경로들을 스캔해 런타임 라이브러리를 만드는 시점은
  그보다 늦다. Ark가 항상 부팅 초기에 강제로 register/mount되는 구조이므로,
  스캔 시점에는 이미 /Ark 콘텐츠가 보이는 상태가 보장됨.
- 따라서 PIE에서 정상 동작한 것은 우연이 아니라 현재 로딩 순서상 항상
  재현되는 결과로 판단.

------------------------------------------------------------
3. Lyra / D1(D:\Project\D1) 대비 구조적으로 비어있는 부분
------------------------------------------------------------
D1은 다음 구조를 갖추고 있음:
- UGameFeatureAction_AddGameplayCuePath (GameFeatureData의 Actions에 추가하는 액션,
  경로 목록을 들고 있음)
- ULyraGameFeature_AddGameplayCuePaths : UObject, IGameFeatureStateChangeObserver
  (커스텀 GameFeaturesProjectPolicies에 옵저버로 등록됨)
  - OnGameFeatureRegistering: 해당 GameFeature의 Action에 등록된 경로들을
    GameplayCueManager에 추가하고 InitializeRuntimeObjectLibrary()를 재호출
  - OnGameFeatureUnregistering: 경로 제거 + 라이브러리 재빌드

즉 D1/Lyra는 "GameFeature 플러그인이 런타임에 register/unregister될 때마다"
GameplayCue 경로를 동적으로 추가·제거하고 라이브러리를 다시 빌드함.

A1에는 이 커스텀 GameFeaturesProjectPolicies 자체가 없고(엔진 기본 정책 사용),
지금 작업은 config에 경로를 정적으로 등록해둔 것뿐이라 위 옵저버 구조가 없음.

------------------------------------------------------------
4. 문제가 될 수 있는 시나리오 (현재는 해당 없음)
------------------------------------------------------------
- Ark가 지금처럼 "항상 켜져 있는 핵심 콘텐츠 플러그인"이 아니라, 나중에
  조건부로 로드/언로드되는 GameFeature(예: DLC성 콘텐츠)로 바뀌는 경우.
  → Ark가 게임 시작 이후 늦게 register되면, 그 시점엔 이미
    GameplayCueManager의 런타임 라이브러리가 다 만들어진 뒤라
    /Ark 하위 GameplayCueNotify가 인식되지 않을 수 있음.
  → Ark가 런타임에 unregister되어도 정적 config 경로는 그대로 남아있고
    라이브러리 재빌드가 안 일어나므로, 이미 로드된 Cue 참조가 stale하게
    남을 수 있음(존재하지 않는 애셋을 가리키는 경고 발생 가능).
- 패키징된 빌드 / 데디케이티드 서버에서는 아직 실제로 검증하지 않음.
  에디터 PIE에서만 확인했고, 원칙적으로는 AssetManager가 부팅 초기에
  Ark를 강제로 스캔·등록하므로 동일하게 동작해야 하지만 실측은 안 됨.

------------------------------------------------------------
5. 결론 / 재검토 시점
------------------------------------------------------------
- 지금 방식(정적 config 등록) 그대로 유지해도 됨. 현재 프로젝트 컨벤션(Ark는
  항상 로드되는 핵심 플러그인) 하에서는 문제가 재현될 시나리오가 없음.
- 아직 쓰지 않는 인프라(D1식 GameFeatureAction_AddGameplayCuePath +
  GameFeaturesProjectPolicies 옵저버)를 미리 만들어둘 필요는 없음.
- 재검토가 필요한 시점: Ark(또는 다른 GameFeature 플러그인)를 조건부로
  로드/언로드하는 구조로 바꾸기로 결정했을 때. 그때 D1의 구조를 참고해
  동적 경로 등록 옵저버를 추가한다.
